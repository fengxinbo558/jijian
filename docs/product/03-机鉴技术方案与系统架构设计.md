## 一、文档目的与技术结论

### 1.1 文档目的

本文说明机鉴如何从动环、网络、BMC、系统、应用、OMS和现场反馈中接收信号，如何确定设备身份与事件关系，如何调用规则、知识库、RAG和只读调查Agent，如何把结果交给系统组、网络组和现场人员，以及如何保证授权、复核、审计和可回退。

### 1.2 一句话架构

机鉴不是“让大模型猜故障”的聊天机器人，而是一个**确定性数据与安全外壳包围AI调查核心**的平台：真实平台提供身份和证据，规则负责硬门禁，RAG提供版本化经验，AI负责综合与解释，人工负责授权和现场决策。

### 1.3 当前技术结论

| 结论 | 当前状态 | 说明 |
|---|---|---|
| 单体原型可运行 | 已实现 | Python标准库HTTP服务、SQLite、静态Web前端，适合本地演示与功能试点 |
| 多源事件可进入统一管线 | 已实现并模拟验证 | 支持告警、SigNoz告警、日志、现场反馈及六类平台模拟接入 |
| 证据化调查链可审计 | 已实现并自动化验证 | 保存原始输入、标准化事实、候选假设、知识命中、提示词/约束版本和八步RAG轨迹 |
| AI模型为可选增强 | 已实现接口，未完成真实模型基线 | OpenAI-compatible模型适配；模型缺失时诚实降级到规则与知识 |
| 现场操作门禁可表达 | 已实现并自动化验证 | 完整SN、机架位、操作许可和复核相互独立，AI不得放行 |
| 生产级大规模承载 | 未验证 | 尚未完成真实监控接入、企业身份、HA、容量压测、数据保留和生产SLO验证 |

## 二、架构原则与责任边界

### 2.1 五项原则

1. **身份不猜。** SN、机架位、端口、拓扑和工单必须来自平台字段、资产系统、扫码/OCR或人工确认，不能由模型从相似文本猜测。
2. **证据先于结论。** 每个事实、假设和建议都必须能回指事件、查询结果或知识版本；无证据时输出“证据不足”。
3. **AI不越权。** AI可以建议下一项只读查询，不能批准断电、拔线、换盘、重启、发布提示词或查看原始敏感数据。
4. **中途恢复即停止。** 排查不是固定流程走到底；每个动作后先验证，恢复则结束，未恢复才进入下一分支。
5. **失败可降级。** 模型、外部调查工具或某个数据源不可用时，系统保留规则、知识、人工粘贴和审计能力，并明确显示降级状态。

### 2.2 AI与确定性系统分工

| 能力 | 确定性系统负责 | AI负责 | 人负责 |
|---|---|---|---|
| 设备身份 | 字段校验、资产映射、冲突检测 | 不得补猜 | 扫码/录入、现场核对 |
| 事件关联 | 明确关联键、拓扑、时间窗、去重 | 提出候选关联原因 | 对高影响合并进行确认 |
| 故障判断 | 已发布规则、阈值、状态机 | 综合异构证据、提出竞争假设 | 接口人与专业组确认 |
| 调查动作 | 只读工具白名单与参数校验 | 选择下一项最有信息量的只读查询 | 批准任何有副作用操作 |
| 现场作业 | OMS快照、许可、复核、审计 | 生成角色化步骤与反馈草稿 | 执行、验证、成功或失败接单 |
| 经验沉淀 | 版本、去重、审核、发布、回滚 | 整理为待审核经验候选 | 审核是否适用及适用范围 |

### 2.3 明确不做

- 不在没有真实字段时用大模型猜“是不是同一台设备”。
- 不公开模型私有思维链；管理员看到的是输入摘要、事实、证据、工具调用、候选假设、排除理由和版本快照。
- 不自动执行关机、重启、拔线、换件或配置变更。
- 不把公开数据集或模拟故障的高分包装成生产准确率。
- 不把详细网络拓扑按想象画成事实；只保存可验证的实体、链路和来源。

## 三、系统范围与上下游

### 3.1 上游数据源

| 来源域 | 典型输入 | 接入方式 | 当前状态 |
|---|---|---|---|
| 动环平台 | 温度、漏水、单路/双路掉电、空调异常 | Webhook、API、消息总线或人工粘贴 | 模拟接入已实现，真实接口待接 |
| 网络平台 | 端口down、抖动、CRC/FEC、光模块、链路告警 | Webhook、Syslog、SNMP转换、API | 模拟接入已实现，真实接口待接 |
| BMC/带外管理 | 电源、风扇、温度、内存、磁盘、SEL | Redfish或厂商API | 契约与公开Mockup测试已具备，真实BMC待接 |
| 系统监控 | kernel、systemd、OOM、磁盘、文件系统、进程 | OpenTelemetry、日志代理、监控API | 日志入口已实现，采集器模板待现场化 |
| 应用与服务 | 错误日志、Trace、指标、依赖超时 | OpenTelemetry/SigNoz API | SigNoz只读查询已实现，真实配置待接 |
| OMS/资产平台 | 工单、完整SN、机架位、操作类型、许可、上下线SN | API或人工导入不可变快照 | 人工导入与状态机已实现，真实OMS API待接 |
| 现场反馈 | 目视异常、扫码SN、光功率、操作结果 | Web表单、移动端、消息适配器 | 现场事件入口已实现，消息平台待接 |

OpenTelemetry官方定义了日志、指标和链路等信号及Collector的接收、处理、转发管线，适合作为系统与应用遥测的中立接入层；遗留Syslog和文件日志仍需要资源属性补全，避免只凭正文猜设备。[OpenTelemetry信号](https://opentelemetry.io/docs/concepts/signals/)、[Collector架构](https://opentelemetry.io/docs/collector/architecture/)、[日志规范](https://opentelemetry.io/docs/specs/otel/logs/)

### 3.2 下游协作对象

| 角色 | 主要输出 | 默认可见范围 |
|---|---|---|
| 系统组接口人 | 系统证据、候选根因、下一项只读查询、是否需要现场 | 与系统域相关的证据摘要和工单状态 |
| 网络组接口人 | 链路实体、端口/模块/线缆候选、分支排查建议 | 网络证据、拓扑片段和现场反馈 |
| 现场操作员 | 完整目标、许可状态、复核要求、操作与验证步骤 | 不展示无关业务原文或管理员轨迹 |
| 双岗复核人 | 工单快照、完整SN、机架位、操作对象、现场确认 | 仅复核所需字段，不承担组长权限 |
| 机房组长 | 队列、超时、夜间升级、复核列表、异常处置 | 本机房管理视图 |
| AI管理员 | 知识、提示词、约束、模型、评测、RAG轨迹 | 脱敏后的AI资产和运行证据 |
| 最高管理员 | 原始记录的受控解封、全局审计、发布治理 | 必须填写理由并二次确认 |

## 四、总体逻辑架构

### 4.1 分层架构

| 层级 | 组件 | 主要职责 |
|---|---|---|
| 接入层 | Webhook、日志入口、SigNoz、平台适配器、实验室、现场表单 | 接收事件、验证来源、保留原始载荷引用 |
| 契约层 | 平台标准契约、设备身份、时间、严重度、拓扑键 | 把不同平台字段映射为统一事件，不丢来源 |
| 事件治理层 | 去重、恢复、维护窗、上游抑制、源健康、冲突检测 | 防止告警风暴、误合并和过期告警 |
| 调查层 | 规则、事实抽取、知识检索、RAG、可选LLM、只读Agent | 形成证据、竞争假设、验证计划和角色化解释 |
| 处置协同层 | 队列、分派、OMS作业、许可、复核、结果回填、CC判断 | 把判断变为安全、可追踪的真实作业 |
| 治理层 | AI资产CMS、版本、导入、去重、反馈、发布、回滚、审计 | 管理知识、提示词、约束、测试集和模型供应商 |
| 存储层 | SQLite原型、审计表、快照、备份 | 保存事件、轨迹、版本和操作记录 |
| 展示层 | 故障中心、真实故障、模拟案例、接入实验室、AI控制台 | 按角色展示不同信息与动作 |

### 4.2 端到端主流程

| 步骤 | 输入 | 处理 | 输出 / 停止条件 |
|---|---|---|---|
| 1. 接收 | 平台事件或人工粘贴 | 校验来源、事件ID、时间、载荷大小 | 无法验证来源则拒绝或隔离 |
| 2. 标准化 | 原平台字段 | 映射域、类型、设备标识、机房、严重度 | 保留原字段来源与缺失项 |
| 3. 身份与关联 | SN、设备名、机架位、端口、拓扑、时间窗 | 明确键去重，检测冲突，禁止文本相似度强行合并 | 身份冲突进入人工确认 |
| 4. 事件治理 | 当前告警、恢复、维护窗、源健康 | 抑制重复与下游噪声，识别恢复 | 无需新事件则更新原事件 |
| 5. 规则与事实 | 标准事件、日志片段 | 提取确定性事实、命中安全规则 | 无证据则标记证据不足 |
| 6. RAG | 事实、域、故障类型 | 召回已发布知识、解释命中原因、保存版本 | 无合适知识则不硬套SOP |
| 7. AI调查 | 脱敏证据、知识、只读工具 | 形成竞争假设，选择下一项只读查询 | 证据足够或无更多安全查询时停止 |
| 8. 人工处置 | 候选判断、权限、工单 | 接口人确认、现场核对、许可与复核 | 未满足门禁不得开始 |
| 9. 验证与闭环 | 操作反馈、三网/业务/告警恢复 | 中途恢复即停止；未恢复进入下一分支 | 成功接单或失败接单均留痕 |
| 10. 经验候选 | 完整过程 | AI结构化整理、去重、适用范围判断 | 人工审核后才可发布 |

## 五、事件接入与标准化设计

### 5.1 统一事件最小字段

| 字段组 | 必需字段 | 说明 |
|---|---|---|
| 来源 | platform、source_event_id、observed_at | 支持幂等和溯源 |
| 分类 | domain、event_type、severity、state | state至少区分触发与恢复 |
| 身份 | device_id及其来源 | 可为完整SN、平台设备ID或资产ID；缺失不能由模型补猜 |
| 位置 | facility_code、rack_position | 现场作业必须有机架位；普通调查允许待补充 |
| 关联 | incident_key、topology_keys、change_id | 仅使用可验证键 |
| 证据 | raw_record_ref、summary、attributes | 原文默认隔离，摘要供普通角色使用 |
| 安全 | sensitivity、redaction_state | 控制是否可以送入模型 |

### 5.2 六类平台适配器

当前实验室为动环、网络、BMC、系统、应用、OMS建立独立开关和统一事件入口。平台断开时返回失败，不伪造“已联动”；重复事件使用来源事件ID实现幂等。真实接入时，每个适配器必须补充鉴权、签名、重放保护、速率限制、超时、重试和死信处理。

### 5.3 遥测采集建议

- Linux主机与应用：优先采用OpenTelemetry Collector或现有日志平台转发，增加host、service、environment和asset_id资源属性。
- 网络设备：先由现有网络监控或Syslog/SNMP平台转换为结构化事件，机鉴不直接替代成熟NMS。
- BMC：优先使用Redfish只读资源与事件；Redfish是面向BMC等平台管理的RESTful标准。[DMTF Redfish规范](https://redfish.dmtf.org/schemas/DSP0266_1.13.0.pdf)
- SigNoz：通过只读Logs API按明确设备标识与受限时间窗查询，限制返回条数与超时。[SigNoz Logs API](https://signoz.io/docs/logs-management/logs-api/overview/)
- 现场：支持复制日志、输入测量值和完整SN；后续移动端可用条码/二维码扫描降低手输错误。

## 六、事件治理、关联与多机事故

### 6.1 关联顺序

1. 明确的incident_key或同一上游事件ID。
2. 资产/拓扑平台给出的实体关系。
3. 同一设备的完整SN或可信平台ID。
4. 同机架、同TOR、同供电域、同动环区域加严格时间窗，形成“候选事故簇”。
5. 文本相似度只能提供候选，不得直接合并。

### 6.2 事件治理能力

| 能力 | 目的 | 当前状态 |
|---|---|---|
| 幂等去重 | 平台重试不重复建单 | 已实现并并发测试 |
| 触发/恢复合并 | 恢复更新原告警 | 已实现 |
| 维护窗抑制 | 计划操作不形成误告警 | 已实现 |
| 上游故障抑制 | TOR或供电故障时抑制大量下游重复事件 | 已实现基础规则 |
| 陈旧告警过期 | 防止旧事件被新信号错误续命 | 已实现 |
| 来源健康 | 区分“设备无告警”与“采集源断了” | 已实现基础状态 |
| 身份冲突 | SN、设备名、位置不一致时阻断现场动作 | 已实现 |

### 6.3 多机事故原则

一个空调、供电、TOR或上联模块可以导致多台设备异常。系统保存“上游事故—下游受影响实体”关系，同时保留每台设备自己的证据和恢复状态。AI可以总结共同模式，但事故合并必须由确定性拓扑或经人工确认的候选关系支持。

## 七、调查引擎与可解释结果

### 7.1 调查输出对象

每次调查至少包含：已确认事实、证据引用、候选假设、支持证据、反证或缺口、置信等级、下一项只读查询、禁止动作、建议协作角色和停止条件。

### 7.2 竞争假设而非单一答案

例如“端口抖动”不能直接等于“模块故障”。系统应并列保留端口服务状态、模块、线缆、对端模块、对端端口和上游网络等候选；更换模块后若告警恢复则停止，未恢复才进入光功率或线缆分支。这样既吸收经验，又避免一条SOP走到底。

### 7.3 管理员可见的推导轨迹

管理员可以看到：

- 收到了哪些来源和事件ID；
- 哪些字段由哪个平台提供，哪些仍缺失；
- 哪些规则命中或未命中；
- 检索了哪些知识版本以及命中原因；
- 模型调用使用了哪个供应商、模型、提示词和约束版本；
- Agent调用了哪些只读工具、参数、返回摘要和错误；
- 最终保留与排除哪些候选及其证据。

不展示模型隐藏思维链；展示的是可审计的产品推理材料和简短理由。

## 八、RAG与知识资产架构

### 8.1 知识资产模型

知识卡不是简单“问答文本”，应包含域、故障类型、触发特征、适用设备/版本、前置条件、排查分支、停止条件、禁止动作、验证方法、来源、审核人、版本和有效期。

### 8.2 检索链路

| 阶段 | 动作 | 审计信息 |
|---|---|---|
| 1 | 整理事件输入 | 事件ID与字段来源 |
| 2 | 抽取事实 | 事实及证据ID |
| 3 | 生成检索条件 | 域、类型、设备、关键词 |
| 4 | 精确与规则召回 | 命中字段与规则 |
| 5 | 本地向量辅助 | 相似度与是否仅作候选 |
| 6 | 排序与裁剪 | 排名、原因、Top K和约束版本 |
| 7 | 组合模型上下文 | 知识版本、脱敏状态、提示词版本 |
| 8 | 生成并校验结果 | 引用合法性、输出状态、失败原因 |

当前本地向量是384维的哈希词与中文n-gram特征，用于轻量相似度辅助，**不是预训练语义Embedding**。生产候选可增加真正的多语言Embedding与Reranker，但必须通过机房日志检索集验证后再发布。

### 8.3 CMS式资产治理

知识、提示词、约束、模型配置、测试用例和运行快照统一进入AI资产目录，具备导入批次、精确重复与近重复检测、关系、反馈、版本、发布、回滚和审计。新处理方式不会删除旧经验，而是形成并列版本或新适用分支；审核时决定生效范围和优先级。

## 九、大模型与只读Agent设计

### 9.1 大模型任务

- 从口语化沟通和异构日志中抽取结构化事实，但不得创造身份字段。
- 把系统、网络、BMC、动环、OMS和现场证据综合成竞争假设。
- 在证据缺口中选择下一项最有价值的只读查询。
- 按系统组、网络组、现场和管理员生成不同深度的解释。
- 将完整处置过程整理为待审核经验候选。

### 9.2 Agent运行契约

当前Agent每轮最多选择一个白名单只读工具，工具参数只允许incident_id和受限limit。应用执行工具后把结果返回模型，循环直到证据足够、没有安全查询或达到轮数上限。模型输出中的证据ID必须存在；未知ID被拒绝。候选状态只允许“候选”或“高可能”，不能直接宣称物理根因已确认。

### 9.3 为什么不是纯工作流

工作流适合OMS状态、许可、复核、CC矩阵、发布和回滚等确定性过程；AI适合日志语言变化、跨源线索组合、候选优先级和解释。两者组合的价值是：**流程保证不越界，AI减少人工读日志、跨窗口拼证据和反复沟通的时间。**

### 9.4 模型失效策略

模型未配置、超时、输出不合规或证据引用失败时，系统回退到规则与本地知识，并显示“模型未参与”或“模型增强失败”。禁止跨厂商自动发送数据；切换合作模型必须由管理员发布新提供商配置。

## 十、现场作业与OMS状态机

### 10.1 建立操作记录

根据已确认业务规则，OMS工单号、完整SN、机架位、是否从重装中发起为必填；机房编码、设备名、操作类型、紧急程度等可选。当前后端对前三项已有硬校验，“是否从重装中发起”仍允许unknown，是必须在试点前修复的P0差距。

### 10.2 独立门禁

| 门禁 | 通过依据 | 不得替代者 |
|---|---|---|
| 身份 | 工单完整SN、扫码/OCR/人工完整SN、机架位一致 | UID灯、设备名相似、模型推断 |
| 操作许可 | 从重装发起或接口人明确批准 | AI判断“应该可以” |
| 复核 | 双岗现场复核或授权远程复核 | 组长默认背书、群里无人回复 |
| 开始操作 | 三项门禁全通过并二次确认 | 单一按钮误触 |

双岗复核人可以是普通现场组员，与组长不是同一权限等级；值班仅一人时，将SN小块照片或扫码结果提交远程确认。紧急夜间作业仍需要找到有权责任人，产品可以升级提醒但不能虚构批准。

### 10.3 状态机

状态按“待身份确认—身份阻断—待许可—许可阻断—待复核—复核阻断—可操作—操作中—成功完成/失败完成”流转。每次变化保存操作者、时间、依据和工单快照。

### 10.4 结束操作

结束不是一个按钮直接结单。操作者需要选择成功或失败、故障详情，填写反馈；涉及备件时记录上线SN与下线SN；再确认信息。成功需记录三网、业务或告警恢复证据；失败需记录已完成步骤、仍存在现象、无法继续原因和已通知接口人。

## 十一、机房等级与CC判断

### 11.1 规则边界

CC是电话通报流程，AI只在触发前提醒，不介入后续每次电话。机房资产中标记核心或普通等级；未知等级时不默认放大权限。

### 11.2 基础矩阵

| 场景 | 核心机房 | 普通机房 | 系统动作 |
|---|---|---|---|
| 单路掉电 | CC | 通常联系接口人与动环，按影响升级 | 依据机房等级和影响输出提醒 |
| 双路掉电 | CC | 设备大面积宕机时升级 | 强提醒并记录依据 |
| 漏水未影响线上设备 | 按核心风险与SOP确认 | 一般不CC | 联系动环、持续监测 |
| 漏水导致核心设备故障 | CC | 按实际影响升级 | 形成事故并关联受影响设备 |
| 高温达到通报阈值 | CC或按SOP | 按阈值和影响 | 立即提醒首次通报时限 |

具体温度阈值和通报制度必须由客户SOP导入，不由通用大模型发明。

## 十二、权限、安全与审计

### 12.1 角色权限

角色包括现场操作员、机房组长、接口人、AI管理员和最高管理员。不同角色看到不同字段；普通现场不应看到无关业务原文，AI管理员默认不能直接打开完整敏感原始数据。

### 12.2 数据出域策略

默认只允许脱敏摘要、证据ID、知识ID和受控属性进入模型。完整SN、内部IP、客户身份、业务载荷和原始日志默认阻断；若客户明确批准外部云模型，仍需按字段级白名单、传输加密、供应商合同和审计策略执行。

### 12.3 原始数据解封

只有最高管理员可在填写原因并二次确认后查看原始记录；系统记录申请人、时间、事件、原因和访问范围。该能力用于溯源，不应成为日常查看方式。

### 12.4 提示词注入与工具安全

外部日志和工具结果视为不可信数据，不能拼接进System提示词；模型只接触结构化工具结果。工具白名单、JSON Schema、参数限制、超时和返回大小由应用层强制，不能只依靠提示词。

## 十三、数据存储与审计模型

### 13.1 当前存储

原型使用SQLite并启用WAL，覆盖事件、输入、审计、设施、知识、提示词、约束、模型提供商、RAG运行、Agent步骤、资产、OMS作业、平台事件、拓扑、生产告警治理、演练、AI资产治理和备份记录。

### 13.2 生产演进

| 数据类型 | 原型 | 生产建议 |
|---|---|---|
| 事务与状态 | SQLite | PostgreSQL或企业关系数据库，主备与时间点恢复 |
| 原始日志 | 受控数据库记录/引用 | 保留在客户日志平台或对象存储，机鉴保存引用与摘要 |
| 检索索引 | 本地结构化检索与哈希向量 | 专用全文与向量索引，版本隔离 |
| 审计 | 数据库表 | 追加写、归档、权限隔离和防篡改策略 |
| 备份 | SQLite在线备份 | 数据库备份、对象存储版本、恢复演练 |

### 13.3 数据保留

生产前需由客户定义事件、原始日志引用、提示词版本、RAG轨迹、现场照片/OCR、工单快照和审计日志的保留周期。删除策略必须区分业务数据、审计证据和AI资产，不能用同一TTL粗暴清理。

## 十四、部署、可用性与可观测性

### 14.1 当前部署形态

当前服务基于Python标准库ThreadingHTTPServer，默认监听127.0.0.1，静态前端和API同进程，适合单机开发、演示和功能试点，不构成生产高可用架构。

### 14.2 试点部署建议

- 部署在客户机房或其授权内网，外部模型默认关闭。
- 反向代理统一TLS、身份认证、请求大小和速率限制。
- 采集适配器与核心服务解耦，单源失败不拖垮调查平台。
- 模型服务、日志平台和OMS均使用最小权限只读账号；写操作单独审批。
- 前后端健康检查、数据库备份、源健康和模型调用状态纳入监控。

### 14.3 生产高可用目标架构

核心API至少双实例，数据库主备，采集事件经持久队列缓冲，外部依赖使用超时、熔断和重试；模型服务不可用时不影响事件接收和现场门禁。备份至少覆盖事务数据库、AI资产版本和审计记录，原始日志由其所属平台负责主备。

### 14.4 自身可观测性

至少监控接入成功率、来源延迟、队列积压、重复率、关联率、身份冲突、RAG耗时、模型失败率、工具调用失败、人工等待、工单超时、备份恢复和权限拒绝。OpenTelemetry Collector也应监控自身接收与导出失败，避免“没有数据”被误判为“没有故障”。[Collector内部遥测](https://opentelemetry.io/docs/collector/internal-telemetry/)

## 十五、容量与性能设计

### 15.1 业务规模基线

当前业务访谈给出的参考规模为单机房约十万台运行服务器、约十名现场运维、日均约二十张工单，夜间和周末可能只有一名值班人员。该数字用于确定设计优先级，不等于当前原型已通过十万设备压测。

### 15.2 性能目标建议

| 指标 | 试点建议值 | 备注 |
|---|---|---|
| Webhook接收P95 | 不高于2秒 | 不包含上游平台延迟 |
| 高优告警入队到可见P95 | 不高于10秒 | 模型调查可异步 |
| 规则与知识基线P95 | 不高于5秒 | 不等待外部模型 |
| AI首轮调查P95 | 不高于30秒 | 按私有模型能力调整 |
| 重复事件新增率 | 接近0 | 同一来源事件ID幂等 |
| 事件接收可用性 | 试点99.5%，生产再定 | 需HA后验证 |

### 15.3 压测维度

需要覆盖突发告警风暴、单TOR影响数百设备、动环区域事故、重复重试、恢复风暴、模型超时、日志平台慢查询、数据库写入竞争和大批量OMS导入。容量结论必须以客户实际事件率而非设备总数单独估算。

## 十六、生产落地差距与实施路线

### 16.1 P0：试点前必须完成

| 差距 | 风险 | 完成标准 |
|---|---|---|
| OMS“是否从重装中发起”后端必填 | 未明确许可来源仍可建记录 | unknown被拒绝，前后端和API测试一致 |
| 企业身份与RBAC | 当前演示头部身份不可用于生产 | 接入SSO/统一身份，角色和机房范围由组织系统下发 |
| 至少一个真实监控源 | 无法证明自动接入 | 70%以上试点故障无需人工复制原始数据的目标可测 |
| 真实资产/拓扑身份 | 设备关联不可完全信任 | SN、机架位、设备名、端口来源可追溯，冲突可阻断 |
| 数据安全评审 | 外部模型可能造成出域 | 字段清单、网络边界、账号权限和审计通过审批 |
| 真实现场评测 | 模拟结果不能代表生产 | 完成盲测、影子运行和人工复核，不自动执行 |

### 16.2 P1：试点期间完成

- 接入第二类监控源，验证跨网络—系统—现场关联。
- 上线私有模型或合作厂商适配器，完成模型对比与降级演练。
- 接入OMS只读接口和资产快照，减少人工录入。
- 建立提示词、知识和约束的测试—双确认发布—回滚流程。
- 完成性能、备份恢复、源健康和故障演练。

### 16.3 P2：规模化前完成

- 服务与采集器解耦、数据库高可用、持久队列和多实例。
- 多机房数据域与权限隔离、分区与归档。
- 真正语义Embedding/Reranker和行业检索集优化。
- 与消息平台、值班、电话升级和资产系统打通，但保持责任边界。
