# 机房重大基础设施事件与 CC 判断设计

> 日期：2026-08-24  
> 状态：待用户书面复核  
> 适用产品：机鉴 IDC AI 故障调查平台

## 1. 背景

现有产品把 CC 提醒主要放在“高温”场景中，这会造成两个问题：

1. 机房重大事件并不只有高温，还包括单路/双路掉电、漏水、核心网络设备宕机、制冷和消防环境异常等。
2. 事件类型本身不能决定是否 CC。相同的单路掉电或漏水，发生在普通机房且没有线上影响时可能不需要 CC；发生在核心机房或已经导致核心设备故障时则可能必须 CC。

因此，产品需要从“高温 CC 判断”升级为“机房重大基础设施事件判断”，并把机房等级、实际影响和证据来源纳入统一规则。

## 2. 设计目标

- 识别供电、制冷、漏水、消防环境、网络和设备影响六类机房事件。
- 明确区分“高风险事件”“需要人工确认”和“已经满足 CC 条件”。
- 支持核心机房、普通机房和等级未确认三种状态。
- 在没有资产系统时支持本地标注核心机房、核心设备；未来用 CMDB/资产系统数据替换。
- 让用户看见 CC 判断使用了哪些事实、命中了哪条规则、还缺少什么信息。
- 一次共同事故只产生一个主事件和一次 CC 提醒，避免每台设备重复通报。
- 保持现有边界：产品只在最开始提醒拨打既有 CC 电话，不实现电话拨打及后续固定通报流程。

## 3. 非目标

- 不自动拨打电话、群呼或代替人工完成 CC 通报。
- 不在第一版中接入真实 CMDB、动环、UPS、PDU、交换机或消防平台。
- 不根据机房名称、设备名称或大模型常识猜测“核心”属性。
- 不把所有掉电、漏水、温度或交换机告警都升级为 CC。
- 不允许大模型单独决定 CC、断电、重启、拔线或更换设备。
- 不在第一版中写死未经用户确认的温度、湿度、电压或影响台数阈值。

## 4. 已确认的业务边界

### 4.1 机房等级

机房等级为：

- `core`：核心机房；
- `normal`：普通机房；
- `unknown`：尚未确认。

第一版由产品内的本地配置进行标注。未来接入资产系统后，以有效的资产系统数据作为主要来源，并保留原本地值、替换时间和来源记录。

### 4.2 普通机房

- 普通机房单路掉电、影响较小或没有设备宕机时，不自动触发 CC。
- 普通机房漏水但未影响线上设备时，不自动触发 CC。
- 普通交换机或单台服务器宕机走正常故障流程，联系 SIM、网络组、动力或接口人。
- 普通机房出现双路掉电、整机房断电、多机宕机等严重情况时，产品显示“等待 SOP/接口人确认”，除非输入已经明确确认需要 CC。

### 4.3 核心机房和核心设备

以下规则已经确认可直接产生一次 CC 提醒：

- 核心机房单路掉电；
- 核心机房双路掉电；
- 漏水已经导致核心交换机等核心设备故障；
- 核心交换机宕机并造成大范围下联中断；
- 温度达到当前机房已配置的 SOP 条件，或现场/接口人已经明确确认达到 CC 条件。

核心交换机异常但冗余仍正常、业务未受影响时，先进入人工确认，不把“设备告警”直接等同于“重大中断”。

## 5. 统一领域模型

### 5.1 机房档案 `FacilityProfile`

| 字段 | 说明 |
|---|---|
| `facility_id` | 稳定的机房标识 |
| `display_name` | 页面显示名称 |
| `criticality` | `core`、`normal`、`unknown` |
| `criticality_source` | `local_config`、`cmdb`、`manual_confirmed` |
| `source_reference` | 资产记录号或本地配置记录号 |
| `effective_at` | 当前等级生效时间 |
| `updated_at` | 最后更新时间 |

机房名称只用于展示，不能参与核心等级推断。

### 5.2 设备角色 `AssetRole`

| 字段 | 说明 |
|---|---|
| `asset_id` | 完整 SN、设备唯一标识或资产编号 |
| `asset_type` | 服务器、交换机、供电设备、制冷设备等 |
| `role` | 核心交换机、普通交换机、服务器、UPS、PDU 等 |
| `criticality` | 核心、普通、未确认 |
| `source` | 本地配置、资产系统或人工确认 |

第一版只需要维护命中场景所需的核心设备名单，不建立完整 CMDB。

### 5.3 基础设施事件 `FacilityEvent`

| 字段 | 说明 |
|---|---|
| `category` | `power`、`cooling`、`water`、`fire_environment`、`network`、`device_impact` |
| `subtype` | 单路掉电、双路掉电、漏水、温升、空调停机、核心交换机宕机等 |
| `impact_level` | 只有告警、冗余降低、部分设备受影响、核心/大面积中断 |
| `affected_scope` | 机房、区域、机柜、设备及完整 SN 列表 |
| `evidence` | 动环告警、日志、现场反馈、资产数据、接口人确认 |
| `source_event_id` | 外部事故号；用于优先合并共同事故 |
| `started_at` | 首次发现时间 |

### 5.4 CC 判断 `CcAssessment`

| 字段 | 说明 |
|---|---|
| `decision` | `required`、`needs_confirmation`、`not_required` |
| `reason` | 面向现场人员的简明原因 |
| `matched_rule_id` | 命中的固定规则编号 |
| `rule_version` | 判断时使用的规则版本 |
| `evidence_ids` | 支撑判断的证据列表 |
| `missing_evidence` | 做出更强结论仍缺少的信息 |
| `reminder_emitted_at` | 本次共同事故首次显示 CC 提醒的时间 |

## 6. 判断流程与规则优先级

统一处理链路为：

```text
收到异常
  → 归一化事件类型与现场对象
  → 查询机房等级和设备角色
  → 评估实际影响范围
  → 匹配固定 CC 规则
  → 输出需要 CC / 等待确认 / 普通处理
  → 继续正常调查或现场处置流程
```

规则优先级从高到低为：

1. **明确确认优先**：监控、现场、接口人或 SOP 输入已经明确 `cc_required=true` 时，产生一次 CC 提醒并记录来源。
2. **已批准核心规则**：核心机房单/双路掉电、漏水导致核心设备故障、核心交换机大范围下联中断等命中确定性规则。
3. **信息冲突**：核心等级、设备角色或影响范围存在冲突时，输出 `needs_confirmation`，列出冲突来源。
4. **信息缺失**：机房等级未知或关键影响证据不足时，输出 `needs_confirmation`。
5. **普通事件**：没有命中以上条件时输出 `not_required`，但仍提供联系接口人和后续调查建议。

`not_required` 只表示“当前证据下不需要 CC”，不表示故障已经解决。

## 7. 第一版判断矩阵

| 机房/对象 | 事件和影响 | CC 判断 |
|---|---|---|
| 核心机房 | 单路掉电 | `required` |
| 核心机房 | 双路掉电 | `required`，页面标为最高等级 |
| 普通机房 | 单路掉电且设备未宕机 | `not_required` |
| 普通机房 | 双路掉电或整机房断电 | `needs_confirmation` |
| 任意机房 | 漏水但未接触设备、没有线上影响 | `not_required` |
| 核心对象 | 漏水导致核心交换机等核心设备故障 | `required` |
| 核心网络设备 | 宕机并造成大范围下联中断 | `required` |
| 核心网络设备 | 异常但冗余正常、业务未受影响 | `needs_confirmation` |
| 普通对象 | 普通交换机或单台服务器宕机 | `not_required`，走正常故障流程 |
| 多设备 | 同机柜、同区域或同上联批量异常 | 建立共同事故后重新判断 |
| 任意机房 | 温升但未达到 SOP 条件 | `not_required` |
| 任意机房 | 达到已配置 SOP 条件或人工明确确认 | `required` |
| 任意机房 | 空调、风扇、水泵、湿度异常但设备未受影响 | `not_required` |
| 任意机房 | 烟雾、火灾、消防系统动作 | 最高风险展示，CC 由 SOP/人工确认 |

## 8. 事件类别与首批识别词

首批规则需要同时支持中文现场描述和常见英文告警，不以关键词单独决定 CC。

### 8.1 供电

- 单路掉电、双路掉电、市电中断；
- UPS 异常、旁路、电池异常；
- PDU、ATS、断路器、线路输入异常；
- 电源冗余降低、整柜或整机房掉电。

### 8.2 制冷与环境

- 温度升高、高温、局部热点；
- 空调停机、制冷能力降低；
- 风扇、水泵异常；
- 湿度异常。

风扇满转只作为温度/散热方向的证据，不能单独确认空调故障或触发 CC。

### 8.3 漏水和天气

- 漏水传感器告警、管路漏水；
- 雨水进入、屋面或墙体渗水；
- 机柜附近积水、设备进水；
- 进水导致短路、服务器或交换机宕机。

### 8.4 消防环境

- 烟雾、火灾；
- 消防系统或灭火系统动作；
- 异常振动等动环事件。

这些事件先纳入识别和风险展示；没有用户 SOP 前不新增自动 CC 规则。

### 8.5 网络和设备影响

- 核心交换机、汇聚/上联设备宕机；
- 上联中断造成多个下联设备不可达；
- 同机柜、同区域、多台服务器同时宕机；
- 普通单机和单端口故障。

## 9. AI、规则与知识库的职责

### 9.1 AI 负责

- 从监控告警、日志、现场口语和接口人描述中提取事件类型、对象、时间和影响描述；
- 将“交换机宕机导致一批下联异常”等零散信息整理成候选共同事故；
- 解释判断用到了哪些证据、还缺少什么信息；
- 根据普通处理或 CC 结果生成沟通摘要。

### 9.2 固定规则负责

- 读取机房等级、设备角色和影响等级；
- 运行规则矩阵并产生 `CcAssessment`；
- 保证同一事故只产生一次 CC 提醒；
- 记录规则编号、版本、输入证据和判断结果。

### 9.3 人工负责

- 确认未知或冲突的机房等级、设备角色和影响范围；
- 根据既有 SOP 确认未配置场景是否需要 CC；
- 实际拨打 CC 电话；
- 决定任何可能影响业务、供电或资产的现场操作。

## 10. 共同事故与重复告警

合并顺序为：

1. 相同外部事故号或监控事件号直接挂到同一个主事件；
2. 相同机房、相邻时间、共同上联或共同动环区域可由 AI 提出“建议合并”；
3. 没有确定拓扑或事故号时，不自动把多个设备告警强行合并；
4. 合并后的设备保留各自原始告警和完整 SN；
5. `reminder_emitted_at` 已存在时不再次显示新的 CC 拨打提醒，只更新影响范围。

## 11. 页面设计

### 11.1 机房等级管理

新增简单管理区，支持：

- 新增机房；
- 标注核心、普通或未确认；
- 查看等级来源和最后更新时间；
- 查看本地值被资产系统替换的变更记录。

### 11.2 重大事件判断卡

事件详情新增一张可审计卡片，按顺序展示：

1. 机房等级和来源；
2. 事件类型和影响范围；
3. 关键设备角色；
4. 使用的证据；
5. 命中的规则；
6. 最终结果和缺失信息。

三种结果需要明显区分：

- `required`：醒目显示一次“请立即按现有 CC 流程拨打电话”；
- `needs_confirmation`：提示联系接口人/SIM/网络组/动力确认；
- `not_required`：显示普通处置建议，避免用户误解为无需处理。

### 11.3 模拟案例

至少新增以下十个可重复演练：

1. 核心机房单路掉电；
2. 核心机房双路掉电；
3. 普通机房单路掉电但设备正常；
4. 普通机房漏水但未影响设备；
5. 漏水导致核心交换机宕机；
6. 核心交换机宕机造成下联批量中断；
7. 同一交换机故障产生多台设备重复告警；
8. 温度升高但未达到 CC 条件；
9. 温度达到已配置 SOP 条件；
10. 机房等级未知，需要人工确认。

## 12. 数据来源与未来接入

第一版使用本地配置和模拟输入。后续接入优先级为：

1. CMDB/资产系统：机房等级、设备角色、位置和完整 SN；
2. 动环/DCIM：供电、温湿度、漏水、烟雾和制冷告警；
3. NMS/交换机平台：核心设备、上联、端口和下联影响；
4. BMC/Redfish：服务器电源、温度、风扇和硬件事件；
5. SigNoz：Linux、应用日志和主机指标。

每个值必须保留来源，外部系统不可用时显示“数据不可用”，不得回退为 AI 猜测。

## 13. 冲突与错误处理

- 资产系统与本地机房等级冲突：显示双方值并进入人工确认；旧值不直接删除。
- 监控告警声称设备宕机但仍有健康信号：保留冲突证据，不确认大面积中断。
- 事件缺少机房或影响对象：允许先建事件，但 CC 判断为等待确认。
- 规则执行失败：不显示“无需 CC”，改为“判断失败，请人工确认”。
- AI 解析失败：保留原始输入并允许人工选择事件类型和影响等级。
- 外部数据超时：显示具体缺失来源，继续使用已经取得的证据。

## 14. 验证标准

### 14.1 规则测试

- 表 7 中每一行至少有一个正向测试；
- 核心/普通/未知三种机房等级均有覆盖；
- 明确 `cc_required=true` 的兼容逻辑继续通过；
- 信息缺失或冲突不能错误输出 `not_required`；
- 普通机房单路掉电和无影响漏水不得误触发 CC；
- 核心机房单/双路掉电必须触发一次 CC 提醒。

### 14.2 共同事故测试

- 相同事故号的多台设备被归入一个主事件；
- 同一事故重复输入只产生一次 CC 提醒；
- 没有共同事故证据时不强行合并；
- 合并后每台设备的原始告警和完整 SN 均可追溯。

### 14.3 页面测试

- 用户能看懂机房等级、影响范围、命中规则和最终结果；
- 桌面端和移动端均可查看重大事件判断卡；
- CC、等待确认、普通处理三种状态视觉上不混淆；
- 十个演练案例均能从页面启动并看到预期结果。

## 15. 行业依据与适用边界

- DMTF Redfish Power 消息注册表覆盖断路器、线路输入、电源组和电源模块等事件：<https://www.dmtf.org/sites/default/files/2026-02/DSP2065_2025.4.html>
- Schneider Electric NetBotz 环境监控范围包括温度、湿度、烟雾和漏水：<https://www.se.com/ae/en/product-range/61830-netbotz/>
- Vertiv 环境监控范围还包括振动、UPS 和热管理设备：<https://www.vertiv.com/en-emea/products-catalog/monitoring-control-and-management/monitoring/liebert-rdu-ex/>

本设计中的 CC 规则以用户确认的现场流程为准；没有明确 SOP 的类别只进行识别、风险展示和人工确认。
