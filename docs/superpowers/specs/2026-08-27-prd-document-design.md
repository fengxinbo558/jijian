# 机鉴 PRD 文档设计说明

**日期：** 2026-08-27  
**状态：** 已确认  
**目标产物：** docs/product/02-机鉴PRD产品需求文档.md 与同名 Word 文档

## 1. 设计目标

本 PRD 同时服务两类读者：

1. 管理者、业务代表和项目负责人需要快速理解目标、范围、主要模块、风险和验收方式；
2. 产品、研发和测试人员需要查找具体页面、字段、状态、角色、异常分支、安全门禁和验收条件。

采用“正文＋同文件附录”结构。正文负责评审和理解，附录负责执行与查询；两者使用同一版本，不拆成容易失去同步的多份文档。

## 2. 飞书目录兼容规则

文档后续会导入飞书，因此 Markdown 和 Word 必须使用真实标题样式，不用加粗段落模仿标题。

- Heading 1 / 二级 Markdown 标题：正文一级章节和附录章节；
- Heading 2 / 三级 Markdown 标题：功能模块、主流程或附录分组；
- Heading 3 / 四级 Markdown 标题：具体页面、需求组、异常分支或验收项；
- 不使用 Heading 4 以下层级，避免飞书目录过深；
- 具体需求使用需求编号、粗体标签和正文，不再增加目录层级；
- 标题不得跳级，同级标题的粒度保持一致；
- 目录页使用静态章节清单，真实标题样式作为飞书自动目录的依据。

## 3. 组织方案及选择

### 3.1 单一超长正文

全部字段、矩阵和验收条件放入功能正文。上下文集中，但评审阅读压力大，同一规则容易在多章重复。

### 3.2 正文与同文件附录

正文讲目标、用户、主流程、模块和验收；附录统一维护权限、字段、状态、异常和测试映射。既支持评审，也支持研发测试查阅，导入飞书后仍是一份文档和一套目录。

**选定此方案。**

### 3.3 主 PRD 与多份独立附件

局部维护方便，但飞书中容易出现入口分散、权限不一致和版本不同步。当前阶段不采用。

## 4. 正文目录设计

正文使用以下十六个一级章节：

1. 文档说明与版本状态；
2. 产品背景、目标与成功标准；
3. 产品范围与非目标；
4. 用户角色与使用目标；
5. 信息架构与页面导航；
6. 故障接入与事件建立；
7. 告警治理与事故关联；
8. AI 调查、RAG 与证据链；
9. 角色协同与现场作业；
10. OMS 工单与现场操作闭环；
11. 动环、机房等级与 CC 提醒；
12. 故障演练、接入实验室与生产近似沙盒；
13. AI 控制台、知识与版本发布；
14. 权限、安全、异常处理与降级；
15. 非功能需求与生产试点要求；
16. 验收标准与版本规划。

### 4.1 角色与页面范围

角色覆盖现场人员、现场组长或复核人、系统组/网络组接口人、AI 运营管理员和最高审计管理员。双岗复核人与组长不强制为同一等级。

页面覆盖故障中心、真实故障、模拟案例、数据来源、告警治理、机房等级、故障演练、接入实验室、AI 控制台和现场操作。

### 4.2 故障与调查范围

需求覆盖 Webhook、SigNoz/Alertmanager、日志上传与粘贴、现场反馈、模拟信号和公开测试数据；覆盖来源健康、确定性设备身份、去重、恢复待验证、维护静默、上游抑制、责任分派、人工纠正和跨平台归并。

AI 调查覆盖原始输入、字段来源、事实提取、规则命中、知识召回、竞争原因、反证、缺失证据、下一项只读查询、模型执行状态和人工责任点。模型不得猜测设备身份或操作许可。

### 4.3 现场作业与 OMS 范围

需求覆盖不可变工单快照、完整 SN 核对、操作许可、单人或双岗复核、开始操作、成功或失败接单、部件上下线 SN、详细反馈和历史查询。

OMS 工单建立阶段的必填项为 OMS 工单号、完整 SN、机架位、是否从重装中发起；其他字段在该阶段为选填。后续安全门禁仍可要求补充操作许可等必要信息。

### 4.4 动环与 CC 范围

覆盖核心、普通和未确认机房，以及单路掉电、双路掉电、漏水、温度、烟雾和核心网络影响等三态判断。CC 只在流程起点提醒人工拨打，不接管后续电话通报。

### 4.5 管理与验证范围

覆盖数据资产、资产治理、RAG 知识、检索测试、提示词、约束、模型厂商、沙盒验证、版本发布、回滚、分析轨迹和审计。个人原型采用两步确认，正式版预留双人审批。

故障演练、接入实验室、公开数据和生产近似沙盒必须与真实故障队列和生产数据库隔离，模拟结果不得冒充生产准确率。

## 5. 附录目录设计

附录不是独立文件，而是位于正文后的同级一级章节：

- 附录 A：角色权限矩阵；
- 附录 B：页面与功能清单；
- 附录 C：必填字段与校验规则；
- 附录 D：状态机与合法转换；
- 附录 E：核心规则、停止条件与禁止行为；
- 附录 F：错误、异常与降级对照表；
- 附录 G：需求与测试映射；
- 附录 H：能力事实状态清单。

## 6. 单条需求记录格式

关键需求包含：

- 需求编号，如 PRD-INC-001、PRD-AI-004、PRD-OPS-006；
- 优先级：P0、P1 或 P2；
- 能力事实状态；
- 目标角色；
- 触发条件与前置条件；
- 主流程；
- 异常与停止条件；
- 数据保存、字段可见性与审计要求；
- 可重复验证的验收标准。

普通重复性需求可以使用紧凑矩阵；高风险、跨角色或异常较多的需求使用完整需求块，避免把长段落全部塞入大表格。

## 7. 事实与范围控制

每项关键能力必须标注为以下状态之一：

1. 已实现并验证；
2. 已实现未接真实环境；
3. 模拟验证；
4. 规划能力；
5. 待确认事实。

不得将模拟平台写成已经连接客户生产平台，不得将规则基线写成真实模型已经执行，不得将公开数据或沙盒通过率写成客户生产准确率。

## 8. 错误与降级设计

PRD 除正常流程外，还必须覆盖：

- 数据源断开、超时、权限不足和格式无效；
- 完整 SN、机架位、设备名或拓扑冲突；
- 重复告警、恢复信号与业务未恢复；
- 知识未命中、知识冲突和模型输出无效；
- 操作许可未确认、复核人同账号、必填项缺失和工单超时；
- 隐藏答案越权查看、模拟数据污染真实队列或生产库；
- 数据库、模型或外部平台不可用时的降级与恢复。

每个异常分支至少说明用户看到什么、系统保存什么、谁负责、是否允许重试以及哪些后续动作必须禁止。

## 9. 验收与测试设计

需求验收采用三层证据：

1. 实现证据：对应页面、接口、数据库或配置；
2. 自动验证：对应单元、API、浏览器、演练或沙盒测试；
3. 真实试点：只有生产数据、真实模型、真实接口和业务人员可以证明的指标。

验收标准不使用“正常”“良好”“智能”等无法测试的词作为唯一结论。没有真实证据时，明确写为“待真实试点验证”。

## 10. 文档视觉与交付设计

- Word 延续立项报告的深蓝与青绿色，但使用更适合密集查询的参考手册式排版；
- 保留封面、文档信息、静态目录、页眉、页脚和变更记录；
- 大矩阵使用精确列宽、重复表头和足够留白，不把长段落塞进窄列；
- Word 和 Markdown 均使用真实标题层级，保证导入飞书后形成上下级目录；
- Markdown 是可追踪内容源，Word 是正式评审和飞书导入版本。

## 11. 完成标准

1. 正文十六章和附录 A-H 全部存在；
2. 主要页面、角色、接入、AI、现场操作、治理、演练和沙盒均有可追踪需求；
3. 关键能力均有事实状态，没有将模拟写成生产；
4. 安全门禁、人工责任、异常分支和降级路径完整；
5. 标题层级能被 Word 和飞书正确识别且没有跳级；
6. Word 逐页渲染无缺字、溢出、表格断裂或页眉页脚错位；
7. 无障碍、表格几何、标题和必要内容审计通过；
8. 正文、附录和立项报告之间不存在关键事实冲突。
