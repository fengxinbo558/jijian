# 故障中心界面重构设计

日期：2026-08-25

状态：待用户书面复核

适用产品：机鉴 · IDC AI 故障调查台

## 1. 背景与问题

现有页面采用“84px 功能栏 + 350px 故障队列 + 详情工作区”的永久三栏结构。随着事件、证据、AI 调查、操作记录和演练功能增加，页面已经出现以下问题：

1. 故障队列始终占据横向空间，事件详情被压窄；
2. 队列使用大量重复卡片，单屏可比较的信息反而很少；
3. 详情把摘要、证据、候选、处置和原始记录同时纵向展开，产生极长页面；
4. 页面级滚动混合了队列滚动和详情滚动，用户容易丢失当前位置；
5. 模拟演练、实时故障和历史记录缺少清晰边界；
6. 用户进入页面后不能立刻判断“现在最需要处理什么”。

本次重构不是换颜色或增加卡片，而是重新划分“找故障”和“处理一个故障”两个工作状态。

## 2. 目标与非目标

### 2.1 目标

- 把故障队列升级为独立的“故障中心”；
- 列表状态下优先支持浏览、筛选、排序和认领；
- 调查状态下给详情完整宽度，避免队列长期挤占空间；
- 桌面端主体固定在一屏高度内，各工作区独立滚动；
- 通过页签和按需展开缩短详情首屏；
- 真实故障、模拟演练和历史事件明确分区；
- 保留现有调查、证据、AI、操作、反馈、权限、知识、演练和审计能力；
- 让按钮使用现场人员能直接理解的动作名称。

### 2.2 非目标

- 本次不重写后端事故模型、AI 调查算法或演练引擎；
- 不删除现有功能或数据库记录；
- 不把所有管理后台都合并进故障中心；
- 不制作完整机房拓扑或数字孪生；
- 不为视觉效果增加无助于作业的动画和装饰。

## 3. 方案比较与决定

### 3.1 方案 A：继续永久左右分栏

优点是切换事件快，改动较小。缺点是队列始终占宽，详情仍然拥挤，无法解决当前核心问题。

### 3.2 方案 B：独立列表页 + 独立详情视图（采用）

进入故障中心先看到全宽列表；点击事件后，同一应用工作区切换到全宽详情，并提供返回列表、上一条和下一条。它最大限度释放详情空间，界面状态清楚，也适合移动端。

### 3.3 方案 C：列表 + 右侧抽屉

适合快速预览，但证据链、AI 调查和现场闭环内容过多，抽屉会再次变成长页面。仅保留为未来的“快速预览”，不作为主调查方式。

## 4. 产品主题与视觉方向

### 4.1 具体主题

这是给 IDC 值班人员、网络组、系统组和管理员使用的“事件作业台”，单一任务是：快速找到当前最重要的事故，并在证据、责任和操作边界清晰的情况下推进处置。

视觉不做通用 SaaS 仪表盘，也不做夸张的科幻大屏。采用“机房运行记录板”方向：信息密度高但层级克制，强调设备标识、状态、时间和下一动作。

### 4.2 设计标记

页面最有辨识度的元素是“事件状态轨道”：每个事件以一条短色轨表达严重程度和处理阶段，详情顶部复用同一轨道显示从发现、调查、等待人工到恢复的当前位置。它编码真实状态，不作为装饰。

### 4.3 色彩

- 墨蓝 `#13242D`：导航、主要文字和高可信结构；
- 雾白 `#F4F7F7`：页面底色；
- 纸白 `#FFFFFF`：工作面；
- 信号青 `#087F8C`：进行中、可执行动作和已确认链路；
- 告警橙 `#D8782C`：等待人工、风险和需关注；
- 故障红 `#C84B4B`：严重故障、阻断和失败。

颜色必须同时配合文字、图标或形状，不单独承担状态含义。

### 4.4 字体

- 中文正文和操作：系统中文无衬线字体栈，优先清晰与稳定；
- 设备 SN、IP、端口、事件编号和时间：等宽字体栈；
- 页面标题只使用较强字重，不使用大面积超大字号。

## 5. 页面信息架构

左侧功能栏保留，但“故障队列”不再作为全局永久侧栏。点击“故障”后进入独立故障中心。

```text
┌──────┬──────────────────────────────────────────────────────────┐
│功能栏│ 故障中心  [待处理] [调查中] [等人工] [已恢复] [模拟演练] │
│      ├──────────────────────────────────────────────────────────┤
│      │ 搜索 / 机房 / 专业组 / 严重度 / 时间 / 只看我的          │
│      ├──────────────────────────────────────────────────────────┤
│      │ 当前重点事件摘要                                         │
│      ├──────────────────────────────────────────────────────────┤
│      │ 全宽紧凑事件列表（列表区域独立滚动）                      │
└──────┴──────────────────────────────────────────────────────────┘
```

点击事件后：

```text
┌──────┬──────────────────────────────────────────────────────────┐
│功能栏│ ← 返回故障列表    事件编号 / 状态       上一条  下一条    │
│      ├──────────────────────────────────────────────────────────┤
│      │ 固定摘要：严重度 / 机房 / SN / 机架位 / 结论 / 下一步    │
│      ├──────────────────────────────────────────────────────────┤
│      │ [概览] [AI分析与证据] [处置协同] [原始记录]              │
│      ├──────────────────────────────────────────────────────────┤
│      │ 当前页签内容（内容区独立滚动）                            │
└──────┴──────────────────────────────────────────────────────────┘
```

页面外壳不再产生超长滚动。顶部栏、事件摘要和页签固定；只有列表内容或当前页签内容滚动。

## 6. 故障列表设计

### 6.1 顶部状态分区

- **待处理**：新事件、未认领或需要首次响应；
- **调查中**：系统、AI 或人工正在收集证据；
- **等待人工**：等待接口人确认、现场操作、权限或双岗复核；
- **已恢复**：监控恢复且已完成业务或人工确认；
- **模拟演练**：所有测试和演练运行，默认不进入前四个真实队列。

每个页签显示数量，但不使用夸张的红色角标。严重事件数量单独标明。

### 6.2 列表形态

桌面端采用紧凑行而不是纵向大卡片。每行固定展示：

- 严重度和当前阶段色轨；
- 事件标题和一句当前结论；
- 机房、设备完整 SN 或网络设备名；
- 专业组和当前责任人；
- 最近更新时间和是否超时；
- 下一步动作，例如“等待 SIM 确认可操作”。

次要信息通过行展开或详情查看，不在列表重复铺开。行高控制在约 72–84px，使常见桌面一屏可见 8–10 条。

### 6.3 筛选与排序

常用筛选直接显示：搜索、机房、专业组、严重度、只看我的。更多筛选收进一个菜单。默认按“严重程度 > 是否超时 > 最近更新”排序。用户切换筛选后保留本次会话状态。

### 6.4 空状态与异常

- 没有待处理事件时显示“当前没有待处理故障”，并提供查看调查中或模拟演练入口；
- 加载失败时保留上一次数据，明确显示更新时间和“重新加载”；
- 搜索无结果时展示当前筛选条件，并提供一键清除。

## 7. 故障详情设计

### 7.1 固定摘要区

摘要区只回答六个问题：

1. 发生了什么；
2. 影响在哪里；
3. 对象身份是否已确定；
4. 当前最可能原因是什么；
5. 结论可信到什么程度；
6. 现在应该由谁做什么。

完整 SN、机架位、端口和数据来源必须能复制。身份冲突、缺失证据或禁止操作必须在摘要中直接显示，不能藏在下方。

### 7.2 页签一：概览

默认页签，包含：

- 当前结论及可信级别；
- 影响范围和关联事件；
- 简化状态轨道；
- 下一项只读查询或人工动作；
- 当前责任人与时效；
- 恢复验证状态。

### 7.3 页签二：AI 分析与证据

包含可审计调查链：接收了什么、身份怎样确认、合并了哪些信号、查了哪些只读数据、候选如何变化、哪些证据支持或反驳、规则在哪里拦截。最高管理员可看到更完整的工具调用和模型输入输出摘要；普通角色只看到与其职责相关的证据和结论。

不展示模型私有逐字思维，不把大段日志伪装成推理。原始载荷通过“查看原文”按需展开。

### 7.4 页签三：处置协同

集中现有人工流程：

- 联系接口人和沟通草稿；
- 是否可断电、是否由重装发起；
- 完整 SN、机架位、UID 和扫码/拍摄确认；
- 单人值班远程确认或双岗现场复核；
- 开始操作、操作中反馈；
- 成功或失败接单、故障详情、上下线备件 SN；
- 三网和业务恢复验证；
- 超时原因与最终确认。

高风险按钮只在条件满足时启用，并明确说明尚缺什么。

### 7.5 页签四：原始记录

包含按时间排序的原始日志、平台事件、OMS 状态、聊天摘要、操作审计和历史同设备记录。默认只展示字段摘要，支持按来源、时间和关键字过滤，再展开原文。

## 8. 角色显示

- **现场人员**：优先看到身份、位置、操作许可、现场动作和恢复验证；
- **系统组 / 网络组**：优先看到所属证据、只读查询、接口人沟通和现场反馈；
- **机房组长 / 复核人**：优先看到待确认清单、完整 SN 与工单对照、风险和确认记录；
- **AI 管理员**：增加调查链、知识命中、提示词版本、模型版本和演练入口；
- **最高管理员**：可查看全部审计信息、系统设置和受控的模型调用摘要。

角色差异不仅是隐藏按钮，也包括默认页签、信息优先级和可见数据范围。服务端权限仍是最终边界。

## 9. 响应式行为

### 9.1 桌面端

- 应用主体高度使用可视窗口高度；
- 功能栏固定；
- 列表与详情均占满剩余宽度；
- 标题、摘要和页签固定，内容独立滚动；
- 宽度足够时，概览内部可使用两列，但不能恢复永久队列分栏。

### 9.2 平板和手机

- 功能栏折叠为底部或顶部导航；
- 筛选项进入抽屉；
- 列表改为紧凑卡片，但每张卡只保留关键信息；
- 详情为独立页面，底部固定当前最重要动作；
- 页签可横向滚动，不能把全部内容一次展开。

## 10. 交互与可访问性

- 所有图标按钮同时提供文字标签或辅助名称；
- 当前焦点、选中页签和键盘焦点清晰可见；
- 表格行可以通过键盘打开；
- 确认、失败、删除或终止等动作不只用颜色区分；
- 支持减少动态效果设置；
- 点击返回列表后恢复原筛选、滚动位置和选中事件；
- 浏览器前进、后退应正确切换列表与详情，而不是丢失上下文。

## 11. 原功能迁移清单

以下能力必须保留，并放入清晰入口：

- 故障搜索、严重度过滤和事件选择；
- 证据链、候选原因、置信信息和反证；
- 原始日志与来源快照；
- AI 调查、只读查询建议和管理员审计；
- 现场操作、双岗/远程复核、SN 与机架位确认；
- OMS 开始/结束、成功/失败接单和备件上下线；
- 三网与业务验证；
- 历史事件、重复派单和同设备记录；
- 角色切换和权限；
- 平台接入、知识库、提示词与发布管理；
- 故障演练与模拟平台；
- 动环重大事件及 CC 前置提醒。

管理类能力继续保留在左侧功能栏对应页面，不塞进故障详情。

## 12. 数据和状态约束

- 仅改变前端组织方式，不改变事件 ID、事故状态和审计记录；
- 列表和详情继续使用现有接口，必要时增加分页或按页签加载；
- 模拟运行必须具有明确 `simulation/drill` 标识，默认过滤出真实队列；
- 详情页签不得因为未打开而丢失正在进行的操作状态；
- 返回列表后不重新创建调查或重复触发只读查询；
- 加载失败、权限不足和数据缺失必须呈现可解释状态。

## 13. 验收标准

1. 1440×900 桌面窗口内，故障中心外壳没有页面级纵向长滚动；
2. 默认列表一屏至少能看清 8 条事件及其下一步；
3. 点击事件进入全宽详情，返回后筛选和滚动位置不丢失；
4. 详情首屏能回答“发生什么、影响哪里、当前判断、谁做什么”；
5. 证据、处置和原始记录通过页签切换，不再一次全部铺开；
6. 真实故障列表默认不出现模拟演练数据；
7. 现场、系统、网络、复核人、AI 管理员和最高管理员看到各自正确视图；
8. 原有功能迁移清单逐项存在可用入口；
9. 390px 宽度下列表和详情可操作，没有横向页面溢出；
10. 键盘可以完成筛选、选择事件、切换页签和返回列表；
11. 现有自动化测试通过，并新增列表/详情切换、页签、筛选保留和角色视图测试；
12. 浏览器截图不再出现当前超长纵向页面。

## 14. 实施边界

本次实施聚焦故障中心的页面外壳、列表、详情页签、滚动模型、角色呈现和演练分流。平台接入实验室、知识库、提示词、权限设置和演练控制器只调整入口与返回路径，不重做内部功能。这样可以解决当前最明显的可用性问题，同时控制重构风险。
