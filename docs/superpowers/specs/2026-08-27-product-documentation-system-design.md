# 机鉴产品文档体系设计

**日期：** 2026-08-27  
**状态：** 待用户审核  
**适用产品：** 机鉴 · IDC AI 故障调查台  
**主要用途：** 公司内部立项、产品与研发协同、AI能力评审、测试验收及生产试点准备

## 1. 背景与目标

机鉴当前已经积累了功能设计、实施计划、测试报告、模拟场景、知识卡、提示词、Agent与RAG代码等材料，但这些材料主要面向开发过程，尚未形成管理者、产品、研发、测试和试点实施人员都能使用的正式产品文档。

本次不再新建大量互相重复的文档，而是建立十份核心文档。每份文档有明确读者、目的和事实来源，同时共同引用一套统一的产品事实、术语、假设和证据，避免出现以下问题：

- 立项报告声称已经具备的能力，代码或测试实际上尚未具备；
- PRD、技术方案和测试标准对同一功能的描述不一致；
- 把模拟数据、规则基线、测试模型桩误写成真实AI能力；
- 用知识卡数量代替知识质量和场景覆盖；
- 把现场经验直接当成跨客户、跨厂商都成立的通用结论；
- 把计划接入的外部平台写成已经接入生产环境。

## 2. 文档组织方案

正式产品文档统一保存在 `docs/product/`，Markdown作为可追踪的内容源；需要正式流转时再生成Word或PDF版本。设计过程文档仍保存在 `docs/superpowers/`，不与正式交付材料混在一起。

### 2.1 十份核心文档

| 编号 | 文档 | 主要读者 | 解决的问题 | 优先级 |
|---|---|---|---|---|
| 01 | 产品立项报告 | 管理者、项目负责人 | 为什么要做、解决什么问题、投入和阶段目标是什么 | P0 |
| 02 | PRD产品需求文档 | 产品、研发、测试、业务代表 | 产品具体做什么、不做什么、怎样验收 | P0 |
| 03 | 业务场景与流程说明 | 现场、系统组、网络组、产品、测试 | 真实故障从发现到恢复和接单怎样流转 | P0 |
| 04 | 总体技术架构设计 | 架构师、研发、运维 | 系统、数据、集成和部署怎样组成 | P0 |
| 05 | AI、Agent与RAG专项设计 | AI研发、产品、评审人员 | AI在哪些环节提效，如何受证据和责任约束 | P0 |
| 06 | 大模型选型与评测报告 | AI研发、采购、管理者 | 选什么模型、为什么、真实效果和成本如何 | P0，但须在真实模型测试后定稿 |
| 07 | 数据接入与平台集成方案 | 系统组、网络组、集成研发 | 日志、告警、BMC、动环、OMS等怎样合法接入 | P0 |
| 08 | 测试与生产试点验收方案 | 测试、业务代表、试点负责人 | 如何证明系统可用、安全且有提效 | P0 |
| 09 | 安全、权限与责任边界说明 | 安全、管理者、各作业角色 | 谁能看、谁能改、谁确认、AI不能做什么 | P0 |
| 10 | 部署运维与用户操作手册 | 部署人员、管理员和终端用户 | 怎样安装、配置、使用、排错、备份和回滚 | P1 |

不再单独建立几十份零散文档。角色矩阵、状态机、接口清单、测试用例、提示词清单、知识来源表等作为上述文档的章节或附件存在。

### 2.2 建议编制顺序

1. 产品立项报告；
2. PRD产品需求文档；
3. 业务场景与流程说明；
4. AI、Agent与RAG专项设计；
5. 总体技术架构设计；
6. 数据接入与平台集成方案；
7. 安全、权限与责任边界说明；
8. 测试与生产试点验收方案；
9. 大模型选型与评测报告；
10. 部署运维与用户操作手册。

模型选型报告可以先建立评测框架，但不能在没有接入候选模型和运行测试集之前写出最终推荐结论。

## 3. 统一事实规则

每项关键能力必须标注下列状态之一：

| 状态 | 定义 | 文档允许使用的表述 |
|---|---|---|
| 已实现并验证 | 当前代码可运行且有相应测试或操作证据 | “当前已支持” |
| 已实现未接真实环境 | 代码或接口存在，但没有连接客户生产平台 | “已具备接入能力，待真实环境验证” |
| 模拟验证 | 只在合成、公开或沙盒数据上运行 | “已完成模拟验证，不代表生产准确率” |
| 规划能力 | 尚未实现或只有设计 | “计划建设” |
| 待确认事实 | 来自回忆、推测或缺少证据 | “待业务方确认” |

当前必须在所有正式文档中保持一致的事实包括：

- 当前运行模式为规则与本地知识基线，真实大模型尚未启用；
- 已实现轻量混合RAG、可审计检索轨迹和知识治理，但当前向量能力不是预训练语义Embedding模型；
- 已实现单个只读调查Agent的协议、工具白名单、模型调用和轨迹记录，但真实模型Agent尚未完成生产验证；
- SigNoz、OpenTelemetry、HolmesGPT、BMC、动环、NMS和OMS均存在接入方案或模拟入口，不得写成已经连接客户生产数据；
- 模拟测试通过只证明流程、规则、安全边界和软件实现达到相应测试要求，不等于生产故障定位准确率；
- AI不负责猜测设备身份、批准断电、执行更换硬件或替代人工责任确认。

## 4. 正式文档通用结构

每份正式文档至少包含：

1. 文档版本、状态、负责人、审核人和更新时间；
2. 文档目的、适用对象和适用范围；
3. 已确认事实；
4. 假设与待确认事项；
5. 主体内容；
6. 范围外事项；
7. 风险与依赖；
8. 验收或决策标准；
9. 证据和参考来源；
10. 变更记录。

涉及数值时必须注明来源和性质。例如“日均约20个工单、机房约10万台运行服务器、约10名现场运维人员”属于用户提供的场景基线，不能直接扩展为行业平均值。提效比例在真实基线测量前只能写成待验证目标，不写成既成收益。

## 5. 知识资产建设原则

### 5.1 不以知识卡数量作为质量证明

现有知识卡只视为产品机制和界面的种子数据。正式材料不突出固定数量，也不以数量说明知识库成熟度。知识库质量使用以下指标衡量：

- 关键故障域覆盖率；
- 每条知识的来源可核验率；
- 适用条件完整率；
- 反证和停止条件完整率；
- 检索命中后对正确下一步的帮助程度；
- 过期、重复和冲突知识的处理时效；
- 真实处置反馈对知识有效性的支持情况。

### 5.2 来源优先级

| 等级 | 来源 | 使用方式 |
|---|---|---|
| A | 国际标准、Linux内核及主流开源项目官方文档 | 可作为通用事实来源，保留版本和发布日期 |
| A | 设备或软件厂商官方手册、错误码、消息注册表和排障指南 | 仅用于明确厂商、型号、版本范围 |
| B | 有许可证和来源说明的公开数据集、官方示例和测试工具 | 用于测试和样例，不冒充客户现场数据 |
| B | 客户正式SOP、资产规则和监控规范 | 仅在客户授权范围内使用，并标明组织适用性 |
| C | 经审核的现场经验和历史工单 | 作为经验候选，保留适用条件、失败案例和审核人 |
| D | 博客、论坛、口述推测和大模型生成内容 | 只能用于发现线索，不能直接发布为正式知识 |

### 5.3 每条正式知识的最小字段

- 唯一标识、版本、状态、领域；
- 标题和适用对象；
- 适用厂商、型号、系统或版本；
- 可观察症状和原始信号；
- 支持证据与竞争原因；
- 反证和容易误判的情况；
- 必需上下文与缺失信息；
- 只读验证步骤和分支条件；
- 可以安全建议的动作；
- 停止条件和禁止推断；
- 来源链接、文档名称、版本、发布日期和摘录定位；
- 编制人、审核人、审核日期和复审日期；
- 实际使用次数、成功支持次数、失败或不适用反馈。

知识更新采取“新增版本”而不是直接覆盖旧版本。新经验与旧经验不同不代表旧经验自动失效；系统按适用条件分别保留，并把冲突交给人工审核。

## 6. 首批可信知识来源方向

首批扩充优先使用以下官方来源，先建立来源登记，再提炼知识：

1. Linux Kernel RAS、EDAC、Machine Check、PCIe和NVMe相关管理文档；
2. DMTF Redfish Specification、Data Model、Message Registry、LogService和TelemetryService；
3. OpenTelemetry日志、资源、系统、硬件、进程和网络语义规范；
4. systemd journal字段、journalctl、coredump和服务状态官方文档；
5. 网络厂商关于端口抖动、CRC、FEC、DOM光功率、模块和光纤排查的官方指南；
6. 存储、文件系统、内核、数据库和常见运行时的官方错误与诊断文档；
7. 经许可证审核的公开日志和故障数据集。

不同厂商的告警阈值、命令和字段不能强行合并为一个通用结论。通用层只描述证据关系；具体阈值和操作放在厂商、型号或客户专属知识中。

## 7. 首份文档：产品立项报告的边界

产品立项报告重点回答：

- IDC故障处理当前在哪些环节存在信息分散、重复沟通、经验依赖和责任风险；
- 机鉴通过监控接入、证据归并、AI调查、知识复用和现场闭环带来什么价值；
- 第一阶段服务哪些角色和场景；
- 当前原型已经证明了什么，仍未证明什么；
- 下一阶段需要接入哪些真实平台和模型；
- 试点需要哪些人员、数据权限、设备范围和验收指标；
- 在不替代人工责任决策的前提下，AI能够节省哪些工作。

立项报告不写虚构的行业市场规模、生产准确率、节省比例和客户案例。无法从当前材料或权威来源确认的内容进入“待验证”部分。

## 8. 审核标准

本设计通过后，正式文档按以下标准编制：

- 十份核心文档之间术语、范围、状态和指标一致；
- 当前能力与规划能力明显分开；
- 模拟、公开数据和真实生产数据明显分开；
- AI、Agent、RAG、规则和人工决策的责任明确；
- 每个重要技术判断都能追溯到代码、测试、标准或官方资料；
- 不以知识卡数量、测试题数量或页面数量替代真实价值证明；
- 文档能够被管理者阅读，也能让研发和测试据此执行。
