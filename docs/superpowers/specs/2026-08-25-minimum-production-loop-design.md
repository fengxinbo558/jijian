# IDC AI 最小生产闭环设计

日期：2026-08-25  
状态：用户已确认  
范围：在现有 AI 调查、现场作业和 OMS 闭环之上，补齐真实数据接入前必须具备的事件治理与可信数据基础。

## 1. 背景与结论

现有产品已经能完成以下演示链路：

1. 监控、日志、现场反馈或模拟平台输入数据；
2. 统一输入格式并绑定设备；
3. 规则、知识库和只读 AI Agent 形成候选原因、反证和下一步；
4. 展示可审计调查轨迹；
5. 生成现场处置卡、SN 复核、安全门和 OMS 成功/失败闭环；
6. 将处理结果沉淀为可审核经验。

但真实平台接入后，一条原始信号不应必然变成事故。生产链路必须先处理重复、恢复、短暂抖动、维护、上下游依赖、数据源故障、资产身份冲突和责任分配。因此新增一层独立的“告警治理层”，位于数据接入和现有事故调查之间。

## 2. 目标

本批次实现：

- 事件、告警、事故三级关系；
- 告警发生、持续、恢复、确认、抑制、静默和过期状态；
- 基础去重、维护窗口和上游故障抑制；
- 资产字段权威来源、更新时间和身份冲突；
- 数据源健康、最后收数、积压、丢弃、重试和覆盖率；
- 部署、配置、固件、资产、端口等变更记录及事故时间关联；
- 值班人员、事故负责人、确认和升级；
- 人工合并/拆分/无关标记反馈；
- 调查耗时、人工采纳和无法确定率等效果指标；
- 公开数据目录、许可证提示、小样本导入和测试结果。

## 3. 非目标

本批次不实现：

- 自动断电、自动重启或自动更换配置；
- 远程控制 BMC、交换机、PDU；
- 电话呼叫和 CC 通话流程；
- 完整资产容量管理和 DCIM 规划；
- 用公开数据替代客户现场验收；
- 将客户原始日志发送到外部模型厂商；
- 以大模型猜测设备身份、拓扑或权限。

## 4. 总体链路

```text
平台 / Webhook / 文件 / 现场 / 公开测试数据
                    │
                    ▼
             原始信号不可变快照
                    │
                    ▼
       格式校验 + 来源健康 + 数据质量评分
                    │
                    ▼
       设备身份对账（权威来源 / 新鲜度 / 冲突）
                    │
                    ▼
  去重 / 恢复 / 维护静默 / 上下游抑制 / 聚合
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   仅记录或被抑制          形成/加入事故
                                  │
                                  ▼
                 现有 AI 调查 + RAG + 只读工具
                                  │
                                  ▼
                  负责人确认 / 现场作业 / OMS
                                  │
                                  ▼
                    恢复验证 / 关闭 / 经验反馈
```

AI 负责跨源归纳、候选原因排序、证据缺口、下一项只读查询、变更关联解释和沟通摘要；确定性程序负责身份、时间、状态、权限、去重、安全门和审计。

## 5. 数据模型

### 5.1 `managed_alerts`

每个可治理告警一条记录：

- `id`：内部告警 ID；
- `fingerprint`：稳定去重指纹；
- `source_system`、`source_event_id`；
- `signal_type`、`site`、`entity_key`、`severity`；
- `lifecycle_status`：`firing|acknowledged|recovered|suppressed|silenced|expired`；
- `incident_id`：可为空；
- `first_seen_at`、`last_seen_at`、`recovered_at`；
- `occurrence_count`；
- `suppression_reason`、`parent_alert_id`；
- `data_quality_json`、`payload_json`。

同一指纹重复到达时增加次数并更新最后出现时间，不重复创建事故。恢复事件更新原告警；事故进入“待业务验证”，不因单一恢复事件直接关闭。

### 5.2 `maintenance_windows`

维护窗口按站点、实体或来源匹配，包含开始/结束时间、原因和创建人。窗口中的告警保存并标记为 `silenced`，不自动派单。

### 5.3 `source_health`

记录每个采集来源：

- 连接状态；
- 最后成功接收时间；
- 接收、拒绝、积压、丢弃和重试计数；
- 预期设备数、最近有数据设备数、覆盖率；
- 检查结果和说明。

“没有设备数据”与“采集器异常”必须是两个不同结论。

### 5.4 `identity_assertions` 与 `identity_conflicts`

资产来源对设备字段提出断言：SN、设备名、机架位、IP、BMC IP、网络端口等。系统按字段级权威顺序和更新时间生成当前身份视图。权威来源互相冲突或数据过期时生成冲突任务；存在阻断冲突时禁止现场操作。

默认权威规则可配置，例如：

- SN、机架位：OMS/CMDB 优先；
- BMC 物理部件：BMC/Redfish 优先；
- 当前端口运行状态：NMS 优先；
- 现场扫码：作为强校验，但不能静默覆盖资产档案。

### 5.5 `change_events`

保存变更类型、对象、操作者、时间、工单/发布号、变更前后快照。事故调查查询可配置时间窗内的变更；时间接近只能提高候选原因优先级，不能单独确认根因。

### 5.6 `duty_rosters`、`incident_assignments`

值班表记录站点、团队、人员、班次和升级负责人。事故分派记录负责人、确认时间、截止时间、延后原因和升级状态。支持夜间单人值班时先确认收到、按优先级排队。

### 5.7 `correlation_feedback`

记录人工执行的合并、拆分、标记无关和纠正原因。反馈不删除原始记录，后续可用于更新规则或训练评估。

### 5.8 `investigation_metrics`

记录首轮分诊耗时、得出结论耗时、AI建议采纳/驳回、人工往返次数、无法确定、错误合并纠正和安全阻断等指标。

## 6. 告警治理规则

处理顺序固定如下：

1. 验证最小字段并保存原始快照；
2. 更新数据源健康；
3. 计算去重指纹；
4. 识别恢复事件并更新已有告警；
5. 检查维护窗口；
6. 检查资产身份冲突；
7. 检查是否有已知上游故障可抑制下游告警；
8. 更新重复告警计数；
9. 判断仅记录、等待聚合或进入事故；
10. 进入事故后执行现有规则、RAG 和 AI 调查。

不会让大模型决定数据是否来自同一设备。身份关联必须来自明确 ID、CMDB/拓扑关系或人工确认。

## 7. API

新增只读/写入接口：

- `GET /api/production/overview`
- `GET|POST /api/production/alerts`
- `POST /api/production/alerts/{id}/acknowledge`
- `POST /api/production/alerts/{id}/recover`
- `GET|POST /api/production/maintenance`
- `GET|POST /api/production/source-health`
- `GET|POST /api/production/identities`
- `GET /api/production/identity-conflicts`
- `GET|POST /api/production/changes`
- `GET|POST /api/production/rosters`
- `GET|POST /api/production/assignments`
- `GET|POST /api/production/feedback`
- `GET /api/production/metrics`
- `GET /api/public-datasets`
- `POST /api/public-datasets/{id}/import-sample`

现有 `/api/ingest/*` 保持兼容。真实平台逐步切换到生产告警入口；手工日志仍可直接进入调查，但页面会明确标记其未经平台告警治理。

## 8. 页面设计

主导航新增“告警治理”，面向接口人、AI管理员和最高管理员：

- 顶部显示数据源健康、有效告警、被抑制、待恢复验证、身份冲突和无人负责数量；
- 告警列表展示生命周期、重复次数、来源、设备、事故关联和抑制原因；
- “可信数据”区域展示来源健康、资产冲突和最近变更；
- “责任与反馈”区域展示当前负责人、确认状态、升级状态及合并/拆分反馈；
- “公开数据测试”区域展示来源、用途、许可证提示、是否已下载、导入数量和测试入口。

现场人员只看到与自己操作相关的告警摘要，不显示全局配置；最高管理员可以看到完整治理依据与原始数据访问审计。

## 9. 公开数据策略

公开数据分三种处理：

1. **可打包小样本**：许可证允许时保存最小样本并注明来源；
2. **本地下载、不纳入产品包**：研究用途或体量较大时，提供下载/导入器，文件仅保存在本地测试目录；
3. **运行时生成**：OpenTelemetry Demo、AIOpsLab、Redfish Mockup 等由本地测试环境生成，不冒充客户生产数据。

首批目录：LogHub、GAIA、OpenTelemetry Demo、Microsoft AIOpsLab、Backblaze Drive Stats、DMTF Redfish Mockups。

## 10. 验收标准

必须通过以下代表性场景：

- 重复告警只产生一个活动告警；
- 恢复事件更新原告警，不直接把事故标为已解决；
- 维护窗口中的告警被静默但可审计；
- 上游交换机故障抑制下游服务器断连；
- 采集器中断被识别为数据源故障；
- 权威资产数据冲突时阻止操作；
- 最近变更显示为候选证据而非确定根因；
- 夜班人员可确认、延后和升级；
- 错误合并可被拆分且保留审计；
- 公开数据导入有来源、许可证和导入报告；
- 现有调查、RAG、角色、现场操作和 OMS 测试继续通过。

## 11. 风险与缓解

- **公开数据与现场差异**：公开数据只验证解析和推理机制，最终阈值和准确率必须现场验收；
- **许可证误用**：数据目录记录许可证和允许用途，受限数据不提交仓库；
- **状态模型过度复杂**：告警状态与事故状态分离，现场页面只展示需要其理解的状态；
- **AI看似合理但错误**：身份、权限和告警状态由确定性程序控制，AI结论必须绑定证据并允许无法确定；
- **十万台规模**：本批次验证合同和逻辑，真实试点前再以消息队列、时序/检索存储替换单机 SQLite 数据面。
