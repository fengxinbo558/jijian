# 机鉴剩余三份核心文档设计说明

## 1. 目标

一次性完成《技术方案与系统架构设计》《AI模型选型报告》《AI评测方案与基线测试报告》，与现有立项报告、PRD组成可直接导入飞书的五份核心文档体系。每份同时交付 Markdown 与 DOCX，保留 Heading 1/2/3 层级。

## 2. 共同事实口径

事实优先级为：当前代码与自动化测试 > 当前仓库内审计报告 > 厂商或标准组织官方资料 > 已确认的业务访谈 > 待验证假设。所有能力都标记为“已实现”“已模拟验证”“已设计未接入”或“待真实环境验证”，不把模拟测试写成生产准确率。

## 3. 文档边界

- 技术文档回答系统如何采集、关联、分析、审计、协同、部署与扩展，并列出生产差距。
- 模型选型回答哪些任务应使用模型、候选模型如何比较、如何兼容合作厂商，以及最终如何通过盲测而不是宣传参数定标。
- 评测文档回答测什么、用什么数据、如何隔离答案、指标与门禁是什么，以及当前基线证明了什么、没有证明什么。

## 4. 核心设计决定

1. 设备身份、事件去重、拓扑关系、权限、断电许可、复核、CC规则和审计由确定性系统负责。
2. AI是调查核心，负责非结构化事实抽取、跨源证据综合、竞争假设、下一项只读查询、角色化解释和经验草稿；AI不得替代授权或现场最终决策。
3. RAG保留知识版本、命中原因、提示词版本、约束版本和八步运行轨迹；现有哈希向量仅是本地辅助，不宣传为语义向量模型。
4. 模型供应商通过 OpenAI-compatible 适配层接入，默认本地或私有化，外部云模型必须显式授权且不得自动跨厂商降级。
5. 生产上线采用“规则与知识基线 + 可选模型增强”，模型不可用时必须诚实降级而非伪造 AI 结果。

## 5. 版式

沿用前两份文档的深蓝、青绿色企业技术文档风格，包含封面、元数据、静态目录、分级标题、紧凑表格、页眉页脚和来源链接。避免装饰性大图；架构关系以小型分层表和流程表表达，防止虚构机房拓扑细节。

## 6. 验证

- 运行全部单元测试，记录测试数、耗时和结果。
- 生成三份 DOCX 后逐页渲染为图片，检查溢出、孤行、表格截断和空白页。
- DOCX 结构检查须通过；Markdown 中的官方链接保留为可点击来源。
